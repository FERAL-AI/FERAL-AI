# Phone task recovery and scoped Chrome permission

Typed phone chat and Theora delegation share the Mac primary conversation and
durable turn contract version 1. The phone saves one canonical request UUID before
dispatch. A verified terminal receipt ends its local wait; ordinary chat prose is
progress. Reconnection queries saved receipts without resending the goal. A local
timeout or cancellation leaves the Mac outcome unknown until readback succeeds.

`node_ack.phone_turn_contract` advertises version 1 only with actual durable turn
and pairing stores and current verified device authority. The read-only
`phone_turn_status_request` accepts only contract version, request ID and session
ID. Its `phone_turn_status` response is found, not_found or unavailable. Only found
carries the exact existing receipt. Foreign-device lookups return not_found.
Readback cannot admit, resume or execute work. Socket, runtime and credential
changes invalidate the captured read authority.

The client keeps unresolved inputs in a bounded atomic local journal. Address
aliases within one saved pairing share its partition. Replacing the pairing does
not import another device's tasks. Corrupt storage is preserved; unsafe writes or
missing recovery capability block new submissions visibly. Terminal readback
updates the existing conversation item rather than adding a duplicate result.

## Selected Chrome and one task step

Chrome remains owned by the Mac conversation that connected its selected tab.
Phone pairing and task approval do not grant Chrome access. The native Browser
screen can review a real current task step, exact selected tab, allowed tools and
an expiry of at most 300 seconds. The one-use local confirmation creates a
volatile grant. Status and revoke retain the captured cleanup identity even when
the screen's active conversation changes.

The local review routes use actual eligible TaskFlow inventory and immutable
terms. They refuse remote callers and fabricated task identities. The task runner
receives an opaque scope; arbitrary copied contexts and sibling tasks cannot use
it. Chrome resource identity remains connection ID, target ID and physical owner
session. Central tool policy, effect ownership and exact action approval still
apply after browser permission is granted.

A newly started model step that encounters its first missing Chrome consent
persists the exact validated next call and completed-call receipts, then waits.
It does not execute the call or continue provider tool dispatch. The Mac user
grants the reviewed browser scope, then explicitly selects Workflows > Resume.
Resume validates current source, task terms, selected resource and permission.
The queued continuation uses the saved call through the existing execution path,
without replaying earlier calls. Permission expiry, revocation or changed terms
cannot turn this checkpoint into an automatic retry. A browser mutation still
needs a separate exact action review.

After restart, a successful registered paired-phone handshake can retain the
current authenticated principal for matching private waiting checkpoints. This
refresh is observational: it writes no task authority, creates no permission and
does not resume work. Fresh Mac consent and explicit Resume remain required.
Legacy shared-key nodes, foreign devices and revoked credentials do not obtain
this authority.

## Private action reviews

Phone decisions require the complete server-issued `task_review` and originating
session. Cards retain exact arguments. Issuer runtime fences prevent a stale
runner from publishing into a replacement runtime. Renewed approval records and
their persisted public cards commit together; interruption preserves the prior
discoverable checkpoint.

An expired browser scope requires fresh explicit Mac consent. Renewing a waiting
model-action review binds the new grant to the same call and physical tab, then
creates a new card. It cannot widen tools, retarget another tab or execute the
action. Superseding a grant permanently invalidates older grants and prepared
reviews. A new explicit decision is still required.

An exact renewal-unavailable refusal allows the phone user to prepare a fresh
review again after restoring the required Mac permission. It does not repeat an
approval decision. Uncertain decision outcomes require reconciliation. Pairing
again cannot substitute for approval authority or a Mac operator credential.

## Acceptance boundary

Processing completion, approval, dispatch and verified external outcome are
distinct. These contracts do not establish a complete shared durable memory
ledger or guarantee arbitrary provider-plan reconstruction after restart.
Synthetic tool peers verify control paths without operating real accounts.
Physical installed-phone networking, audio, configured inference and live Chrome
acceptance remain separate gates, as do signing, notarization and distribution.

Source verification: 1,147 selected integration tests/four skips; CI Ruff; zero
new Mac typing diagnostics; native typecheck/164 checks; final iOS 539 assertions,
unsigned build and actual registered receipt round trip. Candidate and physical
acceptance are recorded separately in the current checkpoint.
